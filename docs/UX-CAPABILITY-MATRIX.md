# UX capability matrix — hand-audited 2026-10-18

Companion to `UX-GAP-REGISTRY.md` (machine-generated heuristics). This page is
the human audit: what each surface can actually do, what proves it, and what
fails if it rots.

Status vocabulary — no softer words are used:

- **VERIFIED** — a test asserts the *effect*, and it passes.
- **PARTIAL** — the surface works, but a named sub-path is stubbed or untested.
- **UNVERIFIED** — code exists, no test asserts the effect. Treated as absent
  for planning.
- **ABSENT** — no implementation found.

## What the matrix says

- **2 of 16** capabilities are VERIFIED at effect level.
- **6** are PARTIAL — they work until a named sub-path doesn't.
- **7** are UNVERIFIED: code exists, nothing proves it.
- **2** are ABSENT (multi-monitor, drag and drop).

The honest reading: WuBuOS has a *demonstrated* Start menu and clipboard, a
working-but-incomplete WM/explorer/terminal, and a long tail that currently
looks like UX in screenshots and behaves like a mock under the hand.

## The four-column rule for every future row

A capability may move from UNVERIFIED to VERIFIED only when all four exist:

1. **Entry point** — reachable from the shell, not only from a test harness.
2. **Effect test** — asserts the resulting state, not the pixels.
3. **Failure path** — what the user sees when it fails (not silence).
4. **Maintenance test** — the named target that fails when this rots.
